# 把 Codex 接入实际工程：工作手册

这份手册补足公众号文章中的具体操作。这里的流程是可选择组合的工程做法；个人既有实践与本次新增建议的边界见 [增补说明](enhancement-notes.md)。

## 1. 先按任务大小选择流程

| 场景 | 够用的过程 | 交付物 |
| --- | --- | --- |
| 已明确的小修复 | 查相关实现 → 复现 → 最小修改 → 相关回归 → diff 自审 | 修改、命令与结果 |
| 陌生项目的新能力 | 探索 → 定义行为 → 按依赖拆解 → 实现与测试 → 审查 | 任务说明、代码、证据 |
| 产品方向仍模糊 | 用 grilling 澄清决策 → 收敛范围 → 规格与验收 | 已确认事项与待决策项 |
| 跨会话长任务 | 读取状态 → 核对当前仓库 → 恢复下一切片 | 当前状态和证据索引 |
| 阶段整体验收 | project-testing 调查与用例 → 确认 → 实施与报告 | 需求到用例映射 |

需要做计划的原因是减少关键未知项。用户已授权且方案清楚时继续实施；只读请求保持只读，重大取舍与高影响外部动作再明确。不要给每个小修改额外加一轮“批准计划”。

## 2. 给陌生项目建立一张短地图

从一个具体用户入口开始，追到业务状态、存储和外部接口。重点看本次变化会触及哪些调用方、数据约定和测试，避免先通读所有文件。

地图回答：入口在哪里、核心模块做什么、有哪些现成能力、什么验证命令真实存在。事实附文件/符号或执行证据，推断单列。现有 README 或 CI 已维护的命令直接引用，避免多处手抄。

没有某项检查时如实写明。是否引入 lint、类型检查或新测试框架，取决于项目风险和实际需求；不为了“流程完整”生成不可执行的空脚本。

## 3. 将任务写成 Issue 的清晰度

可使用 [TASK 模板](../.agents/skills/codex-workflow/assets/TASK.md)。以本仓库练习为例：

| 部分 | 具体内容 |
| --- | --- |
| Background | 清单已能新增、读取，完成命令尚未实现 |
| Objective | 用户完成任务后，下一次进程能读到 completed |
| Scope | 完成指定任务；重复完成；未知 ID；保持其他任务不变 |
| Constraints | 沿用 JSON 格式、pending/completed 状态和退出码；标准库；单进程使用 |
| Acceptance | CLI 主流程跨进程读回；重复操作内容不变；错误保留原数据；已有基线通过 |

这些内容可在本地文档里完成，不要求创建 GitHub Issue。任务若已有 OpenSpec，引用其 specs/tasks；不同文件应有明确职责，不保留两个互相冲突的需求版本。

“改善体验”“提高性能”“更智能”需要继续落实到可观察场景与独立评价标准。Agent 项目还应区分固定代码行为、真实模型效果、成本与用户评价。

## 4. 按行为推进实现和验证

一个垂直切片应贯穿入口、核心逻辑和可观察结果。先让“完成后重新读到状态”通过，再处理重复操作和错误分支。复用适用的现有测试，并让新增断言独立于实现。

使用本包 tdd 时，先按它的要求确认公开测试入口；之后小步红灯→绿灯，后续审查再判断代码整理。整体验收使用 project-testing 时按其两阶段确认。普通修改无需每次重新启动整体验收。

最终把以下证据分开写：代码已实现；某命令已通过；真实服务已调用；本人已认可体验。mock/stub 的边界也要明确。

## 5. 把工程状态留在可恢复的位置

按项目已有组织方式选择文件，不要求统一改目录。例如：

```text
docs/execution/complete-task/
  TASK.md         # 可只引用已有 Spec 和 OpenSpec tasks
  STATE.md        # 当前事实、未提交改动、阻塞与下一步
  VALIDATION.md   # 实际检查、代码状态、结果和缺口
```

重要取舍沿用现有 ADR/设计文件。只有缺少合适记录入口时再新增。对应 [STATE](../.agents/skills/codex-workflow/assets/STATE.md) 和 [VALIDATION](../.agents/skills/codex-workflow/assets/VALIDATION.md) 模板初始都不声称完成。

恢复时先核对分支、提交与 dirty 状态。测试发生于未提交工作区时，要说明证据覆盖了哪些变化；不能只写一个旧提交 SHA。旧报告、历史计划与聊天摘要都是线索，不能单独证明当前代码可用。

## 6. 代码审查和测试互补

审查前冻结比较基准。审查未提交内容时包含 staged、unstaged 和需要纳入的 untracked 文件；审查分支时记录具体基准提交，避免 main 移动后范围悄悄变化。

关注错误条件、兼容性、数据一致性、权限、资源清理和回归。可行动发现应包含触发场景、具体影响、文件/行或符号以及复核方式。没有发现问题时可以如实报告，同时保留未覆盖范围。

实施者自行看 diff 是自审。想做独立审查，需由另一位审查者或明确授权的独立 Agent 基于原始需求、差异及相关上下文判断。独立审查不保证无缺陷；“没有发现”与“已经充分验证”不同。

## 7. 按依赖和资源决定是否并行

只读代码探索、测试缺口分析、不同角度审查较适合并行。接口未定、多个任务改同一文件时，先把依赖收敛。给每个子任务写清输入、职责、可写范围、输出与验收条件；主 Agent 负责集成检查。

当前 Codex 的子 Agent 能力、可见界面和触发规则以客户端及官方说明为准。显式要求委派时仍要限定范围和成本；本包不会因“任务复杂”自动创建子 Agent。[Subagents 官方说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)

Worktree 提供独立代码工作目录，但 Git 元数据仍有关联，端口、数据库、队列、外部账号和测试数据也需要单独隔离。使用前列清资源归属；最终合并后再运行集成验证。[Codex worktree 说明](https://learn.chatgpt.com/docs/environments/git-worktrees)

如果你明确选择 Git 命令行方式，可参考以下手动示例（已有分支名和目标目录需另选）：

```bash
git status --short
git worktree list
git worktree add -b feat/taskbox-review ../taskbox-review HEAD
```

完成并确认成果已保存、工作区无待保留改动后，用 `git worktree remove ../taskbox-review` 清理，不使用强制删除。Codex 管理的 worktree 优先通过其管理入口处理。这里是经过文档核对的示例，本次没有启动并行 worktree 实验。[Git 官方文档](https://git-scm.com/docs/git-worktree)

## 8. 权限与工具决定实际执行边界

AGENTS.md 是行为指令，不能扩大工具的系统权限。Sandbox 限定命令可以访问和修改的资源，Approval 规定什么操作需要额外确认；最终还受到实际客户端、组织和环境设置约束。[官方权限说明](https://learn.chatgpt.com/docs/agent-approvals-security)

读代码、修改项目和执行相关本地检查，按当前任务与现有权限推进。安装依赖、真实服务调用、发信、部署或生产数据变更，需要结合动作和既有授权判断；不能因为它们出现在教程的命令里就直接执行。配置按需要最小化调整，不把宽权限配置当作教程前置条件。

当前 CLI 的参数核对和可复制命令见 [CLI 使用参考](codex-reference.md)。手册不要求更换模型、套餐或全局 config.toml。

## 9. 复盘后选择最小沉淀

先区分需求理解、上下文缺失、实现缺陷、测试缺口、环境问题或流程没执行。再决定把经验放进哪里：行为回归放测试；重复命令放脚本/CI；稳定约束放 AGENTS；复用过程放 Skill；业务取舍放 Spec/ADR。

新增规则要有案例、适用范围和验证办法。偶发问题可以只留修复说明。项目规则、用户长期记忆与团队共享记忆是不同存储；写入长期/共享记忆需用户明确要求。

## 10. 从自己的一个项目开始

使用 [接入工具](adoption.md) 先预览，选择一个小功能验证实际效果。看看 Codex 是否找到正确入口、是否保护原改动、是否运行了有效检查、换会话能否接续。依据这些观察改进流程，再逐步增加工具。
