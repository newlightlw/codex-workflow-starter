# 项目接入与任务定义

## 探索的出口

从用户入口追到本次需求涉及的状态、存储与外部调用，找到已有实现和测试。输出短小的项目地图：相关模块、关键文件/符号、当前真实命令，以及已知事实和待核实事项。

先看项目现有脚本与 CI，再确定检查方式。有测试就复用；没有 lint、类型检查或服务时说明现状，不创建占位命令，也不自动加整套工具链。

## 将需求写成可验收任务

需要形成任务说明时，使用 [TASK.md](../assets/TASK.md)，或复用已有 Issue/Spec：

1. 背景：当前具体问题及证据。
2. 目标：用户可观察的变化。
3. 范围：本次改变的行为及明确后置项。
4. 约束：接口兼容、数据格式、依赖、权限和已有改动。
5. 验收：独立于实现的预期结果、测试入口和人工待验项。

拆解按可验证行为纵向推进：一个切片贯穿输入、业务逻辑、持久化与结果。按真实依赖排序，不先拆成“写完全部前端/后端/测试”再最后拼接。

把能调查的事实与需要用户选择的取舍分开。给待决策问题附影响与推荐选项；已确定内容不重新访谈。用户只要求探索时，在项目地图与计划完成后交付；用户已要求实现且没有关键阻塞时，继续执行。

## 文档职责

AGENTS.md 放稳定规则与条件化入口；业务行为放 Spec；实现取舍放设计/ADR；任务进度和证据各引用其权威文件。已有 OpenSpec 时，TASK 模板的需求与计划栏可以只指向现有 proposal/specs/tasks，不复制第二份基线。

需要新增项目指令时，可参考 [PROJECT-ENTRY.md](../assets/PROJECT-ENTRY.md)，把占位路径和命令替换成实际核实结果后再使用。保留已有项目规则，解决冲突后再合并。
