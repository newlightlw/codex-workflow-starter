# 审查、交付与复盘

## 审查基准

先确定审查对象：未提交改动、某个提交，或相对一个固定基准的变更。记录基准提交；包含未提交内容时同时说明 staged/unstaged/untracked 范围。只看 diff 摘要不能代替阅读相关调用方、错误处理和测试。

审查优先找会影响用户或数据的可行动问题：错误状态、异常路径、接口兼容、数据一致性、权限、资源清理与回归。每条发现给出文件/行或符号、触发条件、具体影响与建议验证。把已证实问题、合理怀疑和风格建议分开；不要为了凑问题制造结论。

仅由同一个实施 Agent 复查时，报告为“自审”。另一个独立 Agent 或人基于任务、diff 与原始材料完成检查，才称为独立审查。独立审查者不应只收到实施者的结论；委派需符合当前授权和可用工具。

## 验证与修复

先运行最相关的现有检查。依据变更影响再扩大到必要的回归、构建和集成测试。失败后区分环境问题、既有失败和本次引入的问题；对后者定位根因、最小修复并重跑。不要降低断言、跳过失败或吞异常来制造通过。

明确测试资源、外部服务和替身。脚本返回成功、真实服务跑通、用户认可体验是不同结论。实际未执行的检查保留未执行状态，不从旧日志或计划推算通过。

## 经验沉淀

有实际失败或重复摩擦时，按证据定位原因，再选最小的长期落点：

| 原因 | 可能的落点 | 如何检验 |
| --- | --- | --- |
| 需求含糊、状态约定冲突 | 规格/决策记录 | 对应场景有明确预期 |
| 行为回归 | 回归测试 | 修复前失败、修复后通过 |
| 命令或环境反复出错 | 已有脚本、运行说明或 CI | 全新环境可执行 |
| 同类过程反复漏步骤 | Skill | 用代表性任务核对行为 |
| 稳定项目约束经常被忽略 | 简短 AGENTS 规则/入口 | 下一次任务能够找到并遵循 |

没有足够复发价值时，只记录本次修复即可。提出规则变更时说明案例、适用范围、维护成本和验证办法。用户当前授权不包含长期/共享记忆写入时，仅提出建议。
